# 2026-10-01 ChatGPT 路由诊断与额度响应兼容设计

## 背景

2026-10-01 对同一 TypeScript PR 审查任务进行了短工作时长 / 长工作时长 A/B 测试，并保存了三份 ChatGPT Web HAR。最大的正常长时样本从任务执行中途才开始记录网络，因此它适合验证“中途加入后还能观察到什么”，不适合与完整短样本比较请求总量或任务起始阶段。

本设计只固化去敏后的结构性证据。原始 HAR、提示词、回答、账号标识、Token、Cookie 和请求头不进入仓库。

## A/B 中可重复观察到的结构

### 短工作时长样本

两个短时样本都出现了服务端可见的 `fast_convo=true`。

- 一个样本在 `thinking_effort=max` 下，reasoning 结束时长约为 1 秒；该次捕获没有看到可用于确认路由结果的 `resolved_model_slug`。
- 另一个样本在 `thinking_effort=max` 下，reasoning 结束时长约为 29 秒；同一 turn 的可见消息元数据中出现 `resolved_model_slug=gpt-5-5-mini`，而其他模型字段仍可见 `gpt-5-6-thinking`。

这些现象说明“只比较请求模型和某一个响应模型字段”不足以描述当前执行路径。

### 正常长工作时长样本

正常样本的 HAR 从执行中途开始，因此没有完整的初始 POST。后续会话记录采用 `messages[]` 形式，当前 turn 最终可见：

- `thinking_effort=max`；
- `resolved_model_slug` 与 `gpt-5-6-thinking` 一致；
- reasoning 结束时长约为 632 秒。

因此解析器需要支持 `messages[]`，并沿当前 turn 取证，不能因为 HAR 从中途开始或会话历史很长而把旧 turn 的字段混入当前判断。

## 诊断原则

### 不把单一信号当作“隐性限制”的证明

下列任一现象单独出现时，只展示为证据，不下结论：

- `fast_convo=true`；
- 请求模型与某个响应字段不同；
- 高 thinking effort 下 reasoning 时间较短；
- 多个响应侧模型字段不一致。

原因包括：页面字段是诊断元数据而不是物理推理后端证明；工作时长还会受任务复杂度、上下文、工具、模型和执行路径影响。

### 当前启发式组合

本版本使用保守的组合提示：

- `fast_convo=true` 且请求模型与优先 resolved/response 模型不同：`restriction_suspected`；
- `fast_convo=true` 且 thinking effort 为 high/max/xhigh/extra-high，同时已观测 reasoning 时长不超过 60 秒：`restriction_suspected`；
- 仅模型字段不同/冲突：`route_anomaly`；
- 仅 `fast_convo=true`：`fast_path_observed`；
- 请求与响应字段一致且没有上述组合异常：`consistent`。

60 秒是用于本地提示的启发式阈值，不是 OpenAI 公布的限流阈值，也不应被解释为 SLA、权益或账号状态证明。即使显示“疑似受限”，仍应通过同任务重复测试、跨 turn 观察或 A/B 复核。

## 当前额度响应兼容

2026-10-01 的页面可见 `/backend-api/wham/usage` 响应已经同时包含多个额度域，包括：

- 顶层主 `rate_limit`；
- 顶层 `additional_rate_limits`，其项目可包含自己的 `rate_limit`；
- ChatPass 等其他独立窗口；
- reset credits 等其他摘要。

旧的递归窗口提取会把这些兄弟额度域混在一起，可能把 reserve / ChatPass 窗口误选为主周额度。

### 约束

- 主额度只从顶层 `rate_limit` 提取。
- `additional_rate_limits`、ChatPass 等独立域不参与主周额度选择。
- 最新主限额摘要独立保存；只要页面自身加载了 `/wham/usage`，就可显示已用比例和重置时间。
- 旧的按日 Analytics 是 Credits/Tokens/Turns 与容量估计的增强证据，不再是“主限额捕获成功”的前置条件。
- 没有按日数据时，不推断 100% Credits 容量。

当前公共入口继续使用 `https://chatgpt.com/codex/settings/usage`，没有根据私有响应变化猜测新的页面 URL。

## 账户与会话限制诊断

除单个 turn 的路由/执行证据外，还保存**最近账户/会话限制状态**，用于区分“某一轮疑似走 fast path”和“服务端已明确返回限制状态”。

### `/backend-api/wham/usage`

只从页面自身已收到的响应白名单化以下字段，并在新响应到来时覆盖最新 Usage 限制快照：

- `rate_limit.allowed`；
- `rate_limit.limit_reached`；
- 主 `rate_limit.primary_window.used_percent`、重置时间与窗口长度；
- `rate_limit_reached_type`，兼容字符串以及 `{ type: ... }` 形态；
- `credits.overage_limit_reached`；
- `spend_control.reached`；
- 有界的 `model_usage` 可用性摘要。

Credits balance、账号/用户标识、完整 `additional_rate_limits`、ChatPass 与原始结构不进入持久化限制状态。

### `POST /backend-api/conversation/init`

只被动观察页面实际发出的精确端点，并持久化有界摘要：

- `blocked_features`；
- `model_limits`；
- `limits_progress`；
- default / intended default model slug。

Usage 与 conversation/init 两类状态独立覆盖更新；某次会话没有重新加载 init 时，不清空最近一次已观测 init 状态。这对中途开始 HAR 或页面没有重复初始化请求的场景尤其重要。

### 判定优先级

服务端明确限制状态优先于单 turn 的启发式路由判断：

1. `allowed=false` 或 `limit_reached=true`：硬限制；
2. 非空 `rate_limit_reached_type`：服务端 rate-limit 状态；
3. `spend_control.reached=true`：spend-control 限制；
4. `overage_limit_reached=true`：超额限制；
5. 非空 `blocked_features`、model limit 明确 `blocked / limit_reached / available=false`，或 `limits_progress.remaining=0`：能力限制；
6. 其余已观测状态显示为未见明确限制。

`model_limits` 非空本身只表示“服务端返回了模型限制记录”，**不自动等于模型被封锁**。UI 展示完整白名单摘要，但只有明确不可用/blocked 或余量归零时才触发限制告警。

## 折叠态异常提示

浮层折叠只隐藏 body；header 保留独立异常徽标。优先级为：

1. 明确账户 hard / rate-limit / spend / overage 限制；
2. 路由组合信号“疑似受限”；
3. 显式功能/模型限制或能力余量耗尽；
4. 路由异常、Credits warning、reset credit 危险/过期；
5. reset credit 临期提醒；
6. 无异常时隐藏。

这样用户不需要展开浮层才能知道有新的异常证据。

## 隐私与证据边界

新增持久化字段仍采用双重白名单，只允许：

- 模型字段与 thinking effort；
- `fast_convo`；
- requested model experience；
- turn use case / mode；
- reasoning 状态与已完成时长；
- 关联 ID、计划类型、时间、来源和由白名单字段计算出的诊断状态。

不保存提示词、回答正文、附件、原始 SSE / WebSocket 帧、HAR、Cookie、Token、请求头或账号资料。
